Характеристики в карточках (🟡): **ГОСТ или ТУ, марка, размер, форма (профиль), технология изготовления (г/к, х/к), форма поставки**.

Цены (🟡): у многих позиций **«цена по запросу»**, у части есть прайс-лист. Внешнего признака складских остатков не видно.

Выводы для проекта:

1. Каталог очень большой (пагинация до 20+ страниц внутри одной марки) и, судя по всему, **частично сгенерирован под SEO**: «марка × размер» как отдельные страницы. Это нормально для сайта, но в приложение его нужно переносить как **номенклатуру с характеристиками**, а не как набор страниц.
2. «Цена по запросу» хорошо согласуется с вашей моделью работы без склада. Значит, в приложении значительная часть товаров будет работать через **запрос цены и КП**, а не через «положить в корзину по фиксированной цене».
3. В каталоге есть товары, которые физически отправляются курьерской службой (проволока, порошки, втулки), и товары, которые везут только грузовиком (листы, длинномерный прокат). Это напрямую влияет на модуль доставки.

## 2. Как подключить существующий каталог и цены

Варианты от лучшего к худшему:

| # | Способ | Когда подходит | Плюсы | Минусы |
|---|---|---|---|---|
| 1 | **Интеграция с учётной системой (1С и т. п.)**, если сайт берёт данные оттуда | Если у компании есть 1С (УТ, КА, ERP, УНФ) | Один источник правды, нет дублирования | Нужен доступ к 1С и программист 1С (или готовый обмен CommerceML) |
| 2 | **Выгрузка из админки сайта** (CSV, XLSX, YML или прямой доступ к БД) | Если каталог ведётся на сайте | Быстро, без участия 1С | Нужно наладить регулярную синхронизацию |
| 3 | **Новая система становится мастером каталога**, сайт позже берёт данные из неё | Если сейчас данные «живут» в Excel | Чистая структура | Нужно согласие на изменение сайта (по правилам это отдельное согласование) |
| 4 | Парсинг сайта | Только как временная мера и **только с письменного разрешения** | Не требует доступов | Хрупко, нет закупочных данных, цены «по запросу» |

💡 Рекомендация: сначала выяснить, **откуда сайт берёт номенклатуру и цены**. Дальше выбрать вариант 1 или 2. Сайт не трогаем.

Как работать с ценами в модели без склада (💡):

- У каждой позиции каталога есть **публичный статус доступности** (из ТЗ): «доступен для заказа», «требует подтверждения у поставщика», «под заказ», «временно недоступен», «индивидуальный запрос цены».
- Публичная цена бывает двух видов: **ориентировочная** (из прайса с датой актуальности) или **отсутствует** («запросить цену»). Окончательная цена фиксируется только в **КП или согласованном заказе**.
- Внутренние данные (поставщики, закупочные цены, сроки, доступное у поставщика количество) хранятся отдельно и **никогда не уходят в клиентский API**.
- Пересчёт единиц (шт ↔ м ↔ кг ↔ т) делается через **теоретическую массу погонного метра или штуки** по сортаменту. Есть ли эти данные на сайте, неизвестно ❓. Продают ли по теоретической или фактической массе, должна решить бухгалтерия.

## 3. Технологический стек

Отправная точка: **разработчик один**, бэкграунд в веб-вёрстке, опыта программирования мало. Поэтому главный критерий — **один язык везде**, максимум готовых решений, минимум своей инфраструктуры.

### 3.1. Мобильное приложение

| Вариант | Общий код iOS/Android | Порог входа для веб-разработчика | Комментарий |
|---|---|---|---|
| **React Native + Expo (TypeScript)** 💡 | ~95% | Низкий (JavaScript, похож на веб) | Сборка iOS в облаке без своего Mac (EAS), обновления «по воздуху», из того же кода можно собрать веб-версию кабинета |
| Flutter (Dart) | ~95% | Средний (новый язык) | Отличная производительность, но Dart отдельный язык, а админку всё равно писать на JS |
| Нативные Swift + Kotlin | 0% | Высокий | Два приложения — не для одного разработчика |
| PWA (веб-приложение) | 100% | Самый низкий | Ограничения push на iOS, нет полноценного присутствия в магазинах |

### 3.2. Сервер и данные

| Компонент | Выбор 💡 | Почему |
|---|---|---|
| Язык | **TypeScript** (Node.js) | Один язык для приложения, админки и сервера |
| Фреймворк | **NestJS** | Модульная структура, где каждая интеграция живёт в отдельном модуле |
| БД | **PostgreSQL** | Транзакции (деньги, статусы), JSONB для характеристик металла, полнотекстовый поиск |
| ORM | Prisma | Схема БД читается как документ, миграции |
| Поиск | Сначала средствами PostgreSQL (полнотекстовый + триграммы); при необходимости **Meilisearch** | Поиск с опечатками и фасетами по марке, ГОСТу и размеру |
| Очереди и повторы | **Redis + BullMQ** | Повторная отправка в ЭДО, ТК и почту при сбоях, опрос банка по расписанию |
| Файлы | S3-совместимое хранилище в РФ | PDF договоров, счетов, подписанные документы |
| Хостинг | **Облако в РФ** (Yandex Cloud, Selectel, VK Cloud, Timeweb) | 152-ФЗ: персональные данные граждан РФ хранятся в РФ |
| Ошибки и мониторинг | Sentry или GlitchTip (self-hosted) | Видеть падения приложения и сервера |

### 3.3. Панель администратора

💡 **Отдельное веб-приложение на React** (Refine или React-Admin), которое работает через **отдельный админский API**. Клиентский и админский API разделены физически, поэтому закупочные цены и маржа не могут «утечь» в мобильное приложение даже по ошибке.

### 3.4. Документы (PDF)

💡 **Шаблоны в формате .docx** (Word) с метками-плейсхолдерами → заполнение (docxtemplater) → конвертация в PDF (LibreOffice или Gotenberg).

Почему .docx, а не HTML: юрист компании сможет **сам** править шаблон договора в Word, без программиста. Каждый сформированный документ хранит **версию шаблона**, **хеш файла** и **снимок данных**, из которых он собран.

## 4. Архитектура

### 4.1. Общая схема

```
 ┌──────────────┐   ┌────────────────────┐
 │ Мобильное    │   │ Веб-админка        │
 │ приложение   │   │ (менеджеры,        │
 │ (Expo)       │   │  бухгалтерия,      │
 └──────┬───────┘   │  логистика, админ) │
        │           └─────────┬──────────┘
   Клиентский API         Админский API
        │                     │
 ┌──────▼─────────────────────▼──────────────────────────┐
 │                 СЕРВЕР (NestJS)                       │
 │  Ядро: Каталог · Цены/КП · Заказы · Закупки ·         │
 │        Финансы · Документы · Доставка · Пользователи ·│
 │        Уведомления · Журнал действий                  │
 │                                                       │
 │  Адаптеры интеграций (сменяемые модули):              │
 │   Банк ─ ЭДО ─ Почта ─ Push ─ СДЭК ─ Дел.Линии ─      │
 │   DaData ─ 1С/сайт(каталог)                           │
 └──────┬──────────────┬──────────────┬──────────────────┘
        │              │              │
   PostgreSQL     Redis (очереди)   S3 (файлы)
```

Принцип адаптеров: ядро знает только внутренние интерфейсы, например `DeliveryProvider.quote()`, `EdoProvider.send()` и `BankProvider.fetchIncomingPayments()`. Чтобы сменить оператора ЭДО или банк, пишется новый адаптер, а ядро не меняется.

Все ключи (банк, ЭДО, ТК) хранятся **только на сервере**. Мобильное приложение никогда не обращается к СДЭК, банку или ЭДО напрямую.

### 4.2. Главный процесс (модель «закупка после оплаты»)

```
Каталог → Корзина/Запрос → Проверка менеджером → КП с ценой и сроком действия
  → Клиент согласует → [Договор/Спецификация] + Счёт → Подписание (ЭДО/иное)
  → Подтверждение оплаты ИЗ БАНКА → Закупка у поставщика(ов)
  → Подтверждение поставщика → Готовность → Доставка/Самовывоз → Закрытие
```

Где автоматизация, а где решение человека:

| Шаг | Автоматически | Решение менеджера |
|---|---|---|
| Предварительная цена | Есть в прайсе и цена актуальна | «Цена по запросу» или прайс просрочен |
| КП | Формирование PDF | Утверждение цены, срока и условий |
| Счёт и договор | Генерация по шаблону | Проверка перед отправкой (на старте всегда) |
| Оплата | Сопоставление выписки банка со счётом | Неразобранные платежи |
| Закупка | Создание черновика заявки поставщику | Выбор поставщика, фиксация закупочной цены |
| Изменение цены или срока у поставщика | Флаг «требует согласования» | Согласование с клиентом |
| Доставка | Расчёт тарифа через API ТК | Собственный транспорт и негабарит |

### 4.3. Независимые статусы (каждый — отдельное поле с отдельной историей)

**Заказ** (жизненный цикл): Создан → Проверяется менеджером → Ожидает подтверждения условий → Ожидает оплаты → Оплата подтверждена → Закупка у поставщика → Поставщик подтвердил заказ → Ожидается готовность продукции → Подготовлена к отгрузке → Организуется доставка → Передан в доставку → Доставлен клиенту → Завершён / Отменён.

**Оплата**: Ожидает оплаты · Ожидает подтверждения поступления · Частично оплачен · Оплачен · Возврат средств · Ошибка оплаты.

**Закупка** (новый, на уровне каждой заявки поставщику): Черновик · Отправлена поставщику · Подтверждена · Цена изменена (нужно согласование) · Отказ поставщика · Оплачена поставщику · Ожидается готовность · Готово к отгрузке · Получено/Отгружено · Отменена.

**Документ** (у каждого документа свой): Формируется · Ожидает проверки · Отправлен клиенту · Ожидает подписания покупателем · Ожидает подписания продавцом · Подписан сторонами · Отклонён · Требует исправления · Аннулирован.

**Доставка** (у каждого отправления свой): Не оформлена · Рассчитывается · Ожидает оформления · Заказана · Принята перевозчиком · В пути · Прибыла в пункт назначения · Готова к выдаче · Доставлена · Проблема · Отменена.

Правила-«замки» между статусами (💡, требуют согласования):

- Перевести заказ в «Закупка у поставщика» можно, только если оплата в статусе «Оплачен» **или** у клиента одобрена отсрочка (кредитный лимит) и есть отметка уполномоченного сотрудника с причиной.
- Перевести оплату в «Оплачен» можно только на основании **банковских данных** (выписка или API) **или** ручного подтверждения бухгалтерией со ссылкой на платёжное поручение из выписки. Квитанция клиента сама статус не меняет.
- Заказ с изменившейся закупочной ценой **не меняет цену клиента**, а переходит в «Ожидает подтверждения условий» с созданием дополнительного соглашения.

### 4.4. Ключевые сущности базы данных

Клиенты и доступ: Организация (реквизиты, источник — DaData и подтверждение пользователя) · Пользователь · Участник организации (роль: владелец, закупщик, бухгалтер, только просмотр) · Адрес доставки · Контактное лицо.

Каталог: Категория · Атрибуты категории (марка, ГОСТ/ТУ, диаметр, толщина, длина…) · Номенклатура (значения атрибутов, единицы, масса на м/шт) · Публичный статус доступности · Публичная цена с датой актуальности.

Внутреннее (только для персонала): Поставщик · Предложение поставщика (закупочная цена, количество, срок, срок действия) · Правила наценки.

Коммерция: Корзина · КП (срок действия) и строки КП со **снимком цены** · Заказ и строки заказа со **снимком согласованной цены**, единицы и количества · История статусов.

Сроки (с историей изменений): предварительный · согласованный с клиентом · подтверждённый поставщиком · фактическая отгрузка · расчётная доставка · подтверждённая доставка.

Закупки: Заявка поставщику · Строка заявки · **Распределение** (строка заказа клиента ↔ строка заявки поставщику, количество). Распределение даёт связь «многие ко многим»: один заказ у нескольких поставщиков и одна закупка на несколько заказов.

Финансы: Счёт · Платёж (из банка: id транзакции, ИНН плательщика, назначение) · Привязка платежа к счёту · Возврат (статус, основание) · Расчёт маржи (только для уполномоченных ролей).

Документы: Договор (тип: разовый / рамочный / существующий бумажный) · Версия договора · Спецификация · Доп. соглашение · Файл (PDF, хеш, версия шаблона, снимок данных) · Отправка в ЭДО (оператор, внешний ID, статус, ошибки) · Письмо (кому, что, когда, ID у провайдера, статус).

Доставка: Отправление (перевозчик, тариф, **расчётная** и **подтверждённая** стоимость, внешние ID, трек-номер) · События отправления (от перевозчика).

Проблемы: Инцидент (причина: отказ поставщика, нет товара, изменение цены, срыв срока, отмена клиентом…) · Действия менеджера · Согласованное с клиентом решение · Связанные финансовые операции.

Общее: Журнал действий (кто, что, когда, старое и новое значение) · Уведомления.

### 5.1. ЭДО — предварительное сравнение (выбор после согласования)

| Оператор | API для своей интеграции | Песочница | Стоимость (🟡, источники противоречат) |
|---|---|---|---|
| **Диадок (Контур)** | Открытая документация, OpenAPI (120+ методов), SDK. В API подключён **Госключ** для подписания физлицами | Есть | Лицензия API: в разных источниках 26 900 ₽/год и 161 000 ₽/год — уточнить у Контура |
| **СБИС / Saby (Тензор)** | Есть, но старый SDK снят с поддержки (замена ExtSDK2, COM) | В документации не заявлена | Тарифы от ~28 800 ₽/год; данные об оплате API устаревшие |
| **Такском** | Есть, SDK .NET, COM, JS, тестовый сервис | Есть | Не найдено |
| **1С-ЭДО (Калуга Астрал)** | Встроен в 1С, отдельный внешний API не основной сценарий | — | От ~7 200 ₽/год (пакет документов) |

Предварительный вывод (💡): для своей интеграции технически удобнее всего **Диадок**. Но решающий фактор — **каким оператором компания уже пользуется**, и есть ли у неё 1С. Если договоры и УПД уже ходят через 1С-ЭДО или СБИС, разумнее встроиться в существующий контур, чем заводить второй.

Обязательные условия юридической значимости, которые учитываем в архитектуре:

- Подписание идёт **только механизмом оператора** с использованием КЭП. Своей кнопки «подписать» нет: приложение показывает статус, полученный от оператора.
- С 1 сентября 2024 года сотрудник, подписывающий от имени организации по доверенности, использует **КЭП физлица + машиночитаемую доверенность (МЧД)** (✅ несколько источников). Система должна это учитывать и для продавца, и для покупателя.
- Если клиент не подключён к оператору ЭДО: (а) приглашение в ЭДО или роуминг между операторами ❓, (б) **бумажный путь**: PDF → подпись и печать → скан → **оригинал по почте**. Статусы «скан получен» и «оригинал получен» хранятся отдельно, (в) для физлиц — подписание через Госключ ❓. Выбор вариантов делает юрист компании.

### 5.2. Доставка — единый интерфейс

Каждый способ доставки — отдельный адаптер:

| Способ | Расчёт | Оформление | Трекинг |
|---|---|---|---|
| СДЭК | API | API (если тариф и груз допустимы) | API |
| Деловые Линии | API | API | API |
| Собственный или наёмный транспорт компании | **Ручная оценка менеджера** (манипулятор, длинномер) | Вручную | Вручную (статусы ставит логист) |
| Самовывоз | — | Адрес, окно, документы | Статус «готов к выдаче» |

Перед запросом к ТК система по **массе, длине и габаритам** заказа отсекает неподходящие способы. Цена от ТК показывается как **«расчётная»**, пока ТК не подтвердит заявку. Для длинномерного проката (листы, трубы, арматура 6–12 м) курьерская доставка почти наверняка не подойдёт, и основным способом станет транспорт компании или наёмный.

3. Кто клиенты: только юрлица и ИП или ещё и физлица? От этого зависят оферта, 152-ФЗ, онлайн-касса и способы оплаты.

6. Срок действия КП по умолчанию?
7. Нужна ли веб-версия личного кабинета, кроме мобильного приложения?
8. Бюджет на внешние сервисы (ЭДО-API, SMS, почта, хостинг, аккаунты в магазинах) и на привлечение второго разработчика или ревьюера?

### Бухгалтерия
1. Какая учётная система (1С какая)? Где сейчас формируются счета, УПД и договоры?
2. Система налогообложения, ставка НДС, как отражать НДС в документах.
3. Продажа по **теоретической или фактической массе**? Округления, допуски, «немерные» длины?
4. Способы оплаты: только безнал по счёту? Нужны ли карта, СБП, B2B-QR?
5. Как сейчас подтверждается поступление денег (выписка из банк-клиента, 1С)?
6. Порядок возвратов и что может удерживаться (по договору).
7. Какой оператор ЭДО используется сейчас? Кто подписывает со стороны продавца, есть ли МЧД?
8. Модель договоров: разовый на каждую поставку, рамочный + спецификации или оба варианта?

### Логистика
1. Есть ли **собственный транспорт** или работаете через наёмных перевозчиков? Как считается стоимость?
2. Откуда физически отгружается товар: со склада поставщика напрямую клиенту или через ваш перевалочный пункт?

4. Какие позиции реально отправляются СДЭК и «Деловыми Линиями», а какие только машиной?
5. Есть ли договоры со СДЭК и «Деловыми Линиями»?
6. Услуги: резка в размер, погрузка и разгрузка, манипулятор — как тарифицируются?

### Вам (разработчику)
1. Какие языки и технологии вы уже знаете (HTML/CSS, JS, PHP…)? От этого зависит окончательный выбор стека.

3. Сколько часов в неделю вы готовы вкладывать?

## 9. Риски и трудозатраты

### 9.1. Основные риски

1. **Объём против ресурсов.** Описанная платформа — это работа **команды из 3–5 человек на 9–12 месяцев**. Одному разработчику с небольшим опытом нужен строгий поэтапный подход, а часть работы стоит отдать на ревью опытному бэкенд-разработчику (безопасность, деньги, персональные данные).
2. **Юридическая значимость.** Договоры, ЭДО и возвраты нужно обязательно согласовать с юристом компании. Ошибка здесь — это деньги и споры.
3. **Источник данных.** Если каталог и цены живут в 1С или Excel без API, синхронизация станет постоянной точкой боли.
4. **Публикация в App Store** для российской компании: регистрация юрлица в Apple Developer (D-U-N-S), возможные ограничения. Нужно проверить заранее ❓.
5. **Противоречие «отсрочка 60 дней» и «закупка после оплаты»** нужно снять до проектирования финансового модуля.
6. **Доставка металла** — в основном ручной процесс (длинномер, манипулятор). API ТК покроют только часть заказов.
7. **Персональные данные (152-ФЗ)**: хостинг в РФ, политика, согласия, журналирование доступа.
8. **Зависимость от одного человека**: нужны документация, бэкапы, доступы на компанию (не на личные аккаунты).

### 9.2. Ориентировочные трудозатраты (часы опытного разработчика, очень грубо)

| Блок | Часы |
